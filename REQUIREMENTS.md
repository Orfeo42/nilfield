# Requirements: scope and design record

`nilfield` reports one hazard class: a nil pointer or a nil interface being dereferenced. This document records what the analyzer reports, the mechanism behind each capability, and what was deliberately left out of scope and why.

The corpus in `analyzer/testdata/src/nilcases` is the yardstick. It holds 43 hazard cases across 47 hazard sites, all covered, plus 13 cases marked out of scope and 16 safe cases that must stay silent. `TestCorpus` turns every marker into a subtest and logs the coverage figure on every run; as of 2026-09-02 it reads `nilfield fully covers 43 of 43 hazard cases (47 of 47 hazard sites)`, with zero false positives, and `go test ./...` is green.

## What the analyzer does

One intraprocedural pass over the AST, walking each function body with a flow-sensitive scope. Two use kinds are hazardous, and only two: a field or method selected through a base (`useSelector`), or an explicit dereference of a base (`useStar`) — `analyzer/expr.go`. A base is either a canonical path rooted at a struct field or a bare local, or an expression with no canonical path (a map/slice index, a type assertion) checked directly against its own nil-origin shape. No other use kind is reported: a map write, a slice index, a channel send or close, or a call through a func-typed value never triggers a diagnostic on its own, only the pointer earlier in the path does (`o.p.m["k"] = 1` and `o.p.fn()` both report `o.p`).

### Path canonicalisation and proofs

`analyzer/path.go` turns an expression into a canonical string path: an identifier, a selector chain (`a.b.c`), or an explicit star (`(*p)`), resolving through a per-scope alias map so a local copy of a field path (`x := o.p`) still resolves back to `o.p`. `isFieldPath`/`isStarPath` classify a canonical path by shape.

A path is proven non-nil in `scope.proven`, populated by `analyzer/guards.go`'s `nilGuards`: an `x != nil`/`x == nil` comparison, negation, and `&&`/`||` decomposition, plus `isDefinitelyNonNil` (an address-of expression or `new(...)`) and `provenFromLiteral` (fields set directly in a composite literal, recursing into nested literals). `analyzer/walk.go` threads these proofs through every statement kind: an `if`/`else` pair proves the opposite branch's guard for whatever follows when one side provably exits (`blockExits`); a tagless `switch { case x == nil: ... }` or a tagged `switch x { case nil: ... }` is read the same way, clause by clause, stopping at the first clause that does not provably exit since execution could have fallen out of an earlier clause without this one's condition ever being tested.

A write anywhere inside a loop body (`walkFor`, `walkRange`), a non-exiting `if` branch, or a non-exiting switch or select clause invalidates every proof and alias that write could have falsified (`scope.invalidate`, `invalidateWrites`), because the body may not run, or may run more than once. A closure launched with `go` is walked with `goroutineScope` instead of the enclosing scope: field and star proofs are dropped, since the guard held at the moment the goroutine was scheduled, not while it runs and another goroutine can mutate the same field in between; a bare local's own nilable state survives, since nothing else can write to a local that is not captured by reference.

### Local nil-state dataflow

A bare local's own value is tracked separately from path proofs, in `scope.nilable` (`analyzer/scope.go`), because a local has no field path to canonicalise and its origin has to be recognised from the assignment shape itself. `analyzer/walk.go`'s `recordAssignment` and `walkDecl` mark a local `isNil`, `typedNil`, or `maybeNil` when it is: declared with no initializer and a nillable type (`var i *inner`); assigned the identifier `nil`; copied from another local already marked (`nilOriginState`); assigned a pointer identifier into an interface-typed local, which is reported as `typedNil` rather than `isNil` since an interface holding a nil pointer is itself non-nil (`assignsTypedNilToInterface`); the result of a map or slice index whose element type is nillable, or a single-form or comma-ok type assertion (`isNilOrigin`); or a result a callee's `nilResults` fact marks nilable (`markNilResultsFromCall`). Any later selector or star use of that local is reported at the state last recorded for it (`checkKnownNil`), which is what lets a dereference of a bare local be caught with no fact and no cross-function reasoning at all. Taking a local's address (`addressTakenNames`) drops its recorded state, since the callee behind `&x` may assign through it.

### The fact system

Everything the analyzer knows about another function is derived from that function's own body and carried as an `analysis.Fact`, so it crosses package boundaries with no annotations and no configuration. Nothing is keyed on a package path or a function name; builtins are resolved through `types.Universe` (`isUniverse`).

- `validates <fields>` (`analyzer/validator.go`): a method returning exactly one unnamed `error` qualifies when, before any statement that can return a nil error (`firstNilErrorReturn`), it rejects a nil receiver field with an early return of something provably non-nil (`rejectingGuard`, `nonNilErrorExpr`). A field the body writes anywhere, or a receiver the body could mutate through a pointer-receiver call or by passing it to another call (`writtenReceiverFields`), is excluded, since a write after the guard could undo what it proved. A caller that checks the error inherits the proof for those fields (`validatorProof`, wired into `recordAssignment` and consumed as `scope.errProof` in `binaryNilGuards`).
- `reports nil argument N` (`analyzer/predicate.go`): a function returning a single `bool` whose body answers `true` for a nil argument, recognised as a leading `if p == nil { return true }` guard (`guardsNilParam`, which requires the guard to be the body's first statement, since an earlier return could answer without reaching it) or as a body that is nothing but `return g(..., p, ...)` forwarding to a callee already carrying the fact at that position (`delegatesNilParam`). Only the one direction is derived: a false result proves the argument non-nil (`callNilGuards`, wired into `nilGuards`), a true result proves nothing, which is what lets a reflection-based helper like gf's `g.IsNil` qualify off its own leading guard while everything its reflection decides afterwards stays unread.
- `asserts argument N` (`analyzer/assert.go`): a function whose body panics unless its Nth boolean parameter holds, recognised as `if !p { panic(...) }`, `if p { return }` followed by a tail that never completes, or delegation to another assert helper passing `p` at the position that helper's own fact names (`assertFormIf`, `assertFormIfReturnThenPanic`, `assertFormDelegation`). A call to such a function proves its argument's guard afterward (`assertedArg`, wired into `walkExprStmt`).
- `never returns` (`analyzer/assert.go`, type in `analyzer/facts.go`): a function whose body ends in a call proven never to return and contains no return statement of its own (`exportNeverReturnsFact`). `callNeverReturns` treats a call to the builtin `panic`, or to another function carrying this fact, as never returning; `blockExits` uses it to decide whether an `if`/switch/select branch exits.
- `nil-safe receiver` (`analyzer/receiver.go`): a pointer-receiver method whose body never dereferences its own receiver without a guard. Exported by re-walking the method body with a second, silent `checker` whose `receiver` field names the receiver parameter; that probe sets `receiverDeref` the moment the receiver path is used unguarded, and the fact is exported only when it never does. `checkKnownNil` skips reporting a method call through a known-nil local when the callee carries this fact.
- `may return nil result N` (`analyzer/results.go`): a function that returns a literal `nil` in a pointer, interface, map, chan or signature-typed result on some path where its error result, if it has one, is also `nil` (`isNilResultKind` excludes slices, since a nil slice behaves like an empty one). `calleeNilResults` looks the fact up at a call site; `isNilOrigin` uses it to treat a single-result call as a nil origin, and `markNilResultsFromCall` marks the corresponding local nilable for a `v, err := f()` assignment. This fact is used only to report the caller's dereference; the producing function itself is never reported for returning the nil.

### The goroutine rule

Covered above under path canonicalisation: `walkGo`/`walkGoroutine` in `analyzer/walk.go` walk an immediately-invoked closure launched with `go` using `goroutineScope`, which drops field and star proofs but keeps local nilable state. A plain `go f(x)` call with no literal body is checked flow-insensitively, since there is no body to walk with an adjusted scope.

## What was deliberately excluded, and why

The corpus marks 13 cases `niloutofscope`, each with a `why` token, so a diagnostic inside one of them fails the build the same way a false positive would. This keeps the scope boundary honest: nothing here is an aspiration, each exclusion is enforced.

**`not-a-dereference` (7 cases).** The hazard is real but is not a nil pointer or nil interface being dereferenced: writing to a nil map (`nil-map-write`), indexing a nil slice (`nil-slice-index`), sending on a nil channel (`nil-channel-send`), closing a nil channel (`nil-channel-close`), calling a nil func value (`call-nil-func-var`), and the two `(nil, nil)` producer shapes where a nil error does not imply a non-nil value (`find-or-nil`, `return-nil-nil`). The `nilResults` fact is still exported for the two producer functions, since a caller that dereferences their result without checking is a real dereference hazard and is covered (`deref-not-found-result`); the producer itself returning `(nil, nil)` is not reported, because that is a nil-value question, not a dereference.

**`construction-site` (4 cases).** `new-service-missing-interface-field`, `new-service-missing-pointer-field`, `new-service-explicit-nil`, and `new-service-by-assignment` are all a struct built with a pointer or interface field left nil: a composite literal omitting a key, a literal setting every key to an explicit `nil`, and `new(T)` followed by only a partial set of field assignments. The panic these produce lands far from the bug, at whichever later call site dereferences the unset field, and that downstream dereference is exactly what `nilfield` already reports (the corpus's `zero-value-struct` case is the same shape without a constructor in between). Reporting at the construction site itself would need a policy for which structs are "wiring" structs and a fact carrying which fields a constructor leaves nil, neither of which exists in this analyzer today. This is a deliberate trade, not an oversight: these four cases are covered by nothing right now, and the corpus keeps them marked `niloutofscope` specifically so that gap stays visible instead of quietly passing.

**`not-nil-analysis` (2 cases).** `swallow-error` (an error checked and then discarded) and `compare-declared-func-to-nil` (`abs != nil`, always true for a declared function) are not questions about a nil value reaching a dereference at all: the first is about whether a checked error is propagated, the second is a comparison whose answer never depends on program state. Both are out of scope on the same one-sentence rule as everything else here.
